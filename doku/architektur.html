Architektur des Quellcodes

Stand: Commit 49a6ba0 · aus src/ abgeleitet · Ergänzung zu requirements/design.html

Rundblick ist eine Electron-App mit drei Prozessen. Die Oberfläche im Renderer kennt nur das Body interface. Der Body koordiniert alle Commands und Queries. Die Domain entscheidet über Commands und schreibt Events in den Event Store. Uhr, IDs, Einstellungen und externe Kalender stellen Provider bereit.

2 Ablauf eines Commands und Rückmeldung

Beispiel: Aufgabe aufs Board ziehen → statusSetzen
  1. client interaktion.ts ruft body.statusSetzen({aufgabeId, status})
  2. Der Proxy ruft window.rb.aufruf('statusSetzen', arg) auf, das läuft als IPC rb:aufruf zum Main-Prozess
  3. ipc.ts prüft den Methodennamen gegen BODY_METHODEN und ruft RundblickBody.statusSetzen
  4. body delegiert an Domain.statusSetzen
  5. domain entscheide(): liest Events mit den Tags aufgabe:<id> und spalten, baut daraus das Kontextmodell, prüft die Regeln und erzeugt StatusGesetzt
  6. eventstore anhaengen(events, {abfrage, nachPosition}): optimistische Sperre. Bei Konflikt versucht es die Domain bis zu 3×
  7. Die Zeile landet in <gerät>.jsonl (mit fsync). CommandStatus {ok:true} geht zurück an die UI
Rückweg: Änderungsmeldung
  1. eventstore meldet seinen Abonnenten {events, fremd:false}
  2. domain wendet die Events auf die Projektion bestand an und ruft beiAenderung-Callbacks
  3. body meldet ['aufgaben','board','kalender']
  4. ipc.ts sendet rb:geaendert an alle Fenster, Preload und Proxy reichen das an main.ts weiter
  5. client Raster frischt die betroffenen Sichten auf, und zwar per Query (liste, board, zeitraum …)

Fremde Geräte: fs.watch sieht eine geänderte fremde .jsonl und liest sie nach 300 ms ein. Ab da gilt fremd:true: Die Domain baut die Projektion komplett neu auf, weil sich Events per HLC dazwischen einsortieren können. Danach läuft alles wie oben ab Schritt 2.
Kalender: EventKit meldet eine Änderung, der Body ruft synchronisieren(), der Cache wird ersetzt und der Body meldet ['kalender','einstellungen'].

3 Commands

Domain-Commands erzeugen nur Events für tatsächliche Änderungen. Ist ein Command schon erfüllt, etwa weil die Aufgabe bereits abgeschlossen ist, liefert er [] und ok. Verletzt er eine Regel, gibt er {ok:false, fehler} zurück, ohne Events zu schreiben.

5 Events (Domain state)

Definiert in src/schema/events.ts, SCHEMA_VERSION = 1. Jede Zeile in der JSONL-Datei ist ein Event mit { id, typ, daten, tags, zeit, meta: { schema, geraet, hlc } }. Die Sortierung über Geräte hinweg regelt die Hybrid Logical Clock (providers/eventstore/hlc.ts). Events werden nie umgeschrieben; ältere Formate rechnet ein Upcaster beim Lesen hoch (jsonl.ts › hochrechnen).

Tag-Konvention: aufgabe:<id> · buchung:<id> · spalten · planung. Über diese Tags schneidet die Domain je Command ihr Kontextmodell zu.

6 Schichtregeln zur Übersetzungszeit

Zur Laufzeit erreichen Aufrufe die Implementierungen (Abschnitt 1). Im Quelltext importiert jede Schicht aber nur Interfaces. Konkrete Klassen kennt allein die Composition Root. npm run lint:deps prüft das (.dependency-cruiser.cjs):

Vondarf importieren
src/client/body/interface.ts, schema/, basis/
src/body/domain/interface.ts, providers/*/interface.ts, schema/, basis/
src/domain/providers/eventstore/interface.ts, schema/, basis/
src/providers/<x>/nur das eigene Verzeichnis, schema/, basis/
src/schema/, src/basis/Blätter, kein Node, kein Electron (gilt auch für body und domain)
src/main/alles (Composition Root)
