Rundblick – Architekturideen

Arbeitstitel · Stand 16.11.2026, Runde 3 (Entscheidungen eingearbeitet, siehe 13) · Electron-Desktop-App für Aufgaben, Board und Kalender mit Google Calendar und iCloud

Rundblick verwaltet eigene Daten (Aufgaben und ihre Buchungen) in einem Event Store und blendet fremde Daten (Termine aus Google Calendar und iCloud) daneben ein. Die Architektur folgt den Vorgaben: Client → Body → Domain/Provider, strikt nach CQS getrennt. Jeder Pfeil zeigt nur auf ein Interface, nie auf eine Implementation.

1 Leitbild & Begriffe

Überblick ist King. Das prägt die Architektur. Fast jede Interaktion endet damit, dass alle sichtbaren Sichten aktuell sein müssen: Liste, Board und Kalender, auch in eingeklappter Form. Daraus folgt:

  • Ein Command meldet nur Erfolg oder Misserfolg zurück. Danach erfahren alle Clients per Änderungsbenachrichtigung, welche Bereiche betroffen sind, und fragen ihre Queries neu ab.
  • Queries müssen sehr schnell sein (Ziel < 5 ms). Deshalb liegen Projektionen im Speicher. Die Datenmenge einer Person (Zehntausende Events) passt bequem hinein.
  • Erfassen muss ohne Kontextwechsel gehen. Dafür gibt es eine zweite Client-Oberfläche, das Schnellerfassungsfenster mit globalem Hotkey.
  • Die Oberfläche ist ein frei teilbares Raster (Entwurf D). Dieselbe Sicht kann mehrfach offen sein, zum Beispiel ein Tages- und ein Monatskalender. Queries sind deshalb parametrisiert (Zeitraum, Filter) und nicht an „die eine“ Kalendersicht gebunden.

2 Architektur im Überblick

Client interface  kennt nur Body interface

Hauptfenster (UI) · Schnellerfassungsfenster (globaler Hotkey) · optional lokales REST API (für Raycast, Kurzbefehle, Skripte) · Menüleisten-Symbol. Nur hier sind Svelte, Electron-IPC, HTTP-Server und globalShortcut bekannt.

▼ Commands / Queries · ▲ CommandStatus / Query-Ergebnisse / Änderungsbenachrichtigungen

Body interface  kennt Domain + Provider interfaces

Koordiniert jede Anfrage. Holt Uhrzeit und IDs von Providern, ruft die Domain auf, fügt eigene und externe Kalenderdaten für Queries zusammen, stößt die Synchronisation an und veröffentlicht Buchungen extern. Parst die Schnellerfassung. Meldet Änderungen.

Domain interface  kennt nur den Domain state provider

Entscheidet über Commands und beantwortet Fragen zum eigenen Zustand. Für jeden Command baut sie sich aus dem Event Store ein Kontextmodell, prüft die Regeln und hängt neue Events an. Queries liest sie aus Projektionen, die laufend aus den Events nachgeführt werden.

  • Aufgaben, Status, Buchungen (auch freie), Board-Spalten mit Kategorien, Tageskapazitäten, Verknüpfungen zu externen Kalendern

Die Regeln werden mit dependency-cruiser im CI geprüft. Ein Verstoß bricht den Build.

Warum bekommt die Domain keine Uhr? Damit ist die Domain deterministisch: Gleiche Events und gleicher Command ergeben immer dieselben neuen Events. Der Body holt jetzt und neue IDs bei den Providern und übergibt sie als Parameter. Das passt zur Vorgabe, dass die Domain nur den Domain state provider kennt.

  • Preload/contextBridge stellt nur drei Funktionen bereit: command(name, payload), query(name, payload) und onChange(cb). Die Typen kommen aus body/interface.ts. Der Renderer sieht also genau das Body interface und nichts sonst. Einstellungen: contextIsolation an, sandbox an, nodeIntegration aus.
  • Body und Domain laufen im Main-Prozess. Die Synchronisation mit den externen Kalendern läuft dort asynchron und blockiert nichts. Wird sie zu schwer, wandert der Kalender-Provider in einen utilityProcess, ohne dass sich am Body etwas ändert.
  • Das lokale REST API ist ein zweiter Client derselben Body-Schnittstelle: POST /commands/schnellErfassen, GET /queries/heute. So lassen sich zum Beispiel Raycast, Alfred oder iOS-Kurzbefehle anbinden (im LAN mit Token).

4 Client interface

Das Client interface ist die Außenseite der App, also das, womit Menschen und andere Programme interagieren. Die Implementierung übersetzt Gesten in Commands und Queries des Body und stellt Ergebnisse dar. Sie enthält keine Fachlogik. Erlaubt ist nur Darstellungslogik: Layout von Überlappungen, Pixel ↔ Zeit, Zoom, Fokuszustand.

Raster & Arbeitsbereiche

Das Hauptfenster ist ein Baum aus Splits (nebeneinander oder untereinander, mit Größenanteilen) und Zellen. Jede Zelle hat eine Sicht und deren eigenen Zustand:

type Knoten = { t: 'split'; richtung: 'nebeneinander' | 'untereinander'; anteile: number[]; kinder: Knoten[] }
           | { t: 'zelle'; id: string; sicht: Sicht | null; zustand: SichtZustand };
type Sicht = 'aufgabenliste' | 'board' | 'tag' | 'mehrtage' | 'timeline';
type SichtZustand = { bereich?: '3tage' | 'woche' | 'monat' | '3monate'; anker?: Datum; zoom?: number; filter?: string };
type Arbeitsbereich = { name: string; wurzel: Knoten };   // z. B. „Überblick“, „Heute“, „Planen“, „Board“
  • Jede Sicht wählt ihre Dichte selbst nach der Zellgröße: voll, kompakt oder als Mini-Zusammenfassung. Das ist reine Darstellungslogik im Client.
  • Jede Zelle fragt ihre eigenen Queries ab (z. B. zeitraum für ihren Ausschnitt). Bei geaendert(['kalender']) fragen alle Kalenderzellen neu ab.
  • Arbeitsbereiche, Zellzustand und Splitter-Anteile sind UI-Zustand pro Gerät, kein Domain state. Sie werden über command.einstellungMerken lokal gespeichert, ohne Events. Das iPhone hat später eigene Layouts.

5 Body interface

Eine Methode pro Command und pro Query. Commands verändern den Zustand und liefern nur einen CommandStatus. Queries verändern nichts und liefern Daten. IDs neuer Objekte stehen im Status, sonst wüsste der Client nicht, was er gerade angelegt hat. Das ist die übliche, CQS-verträgliche Ausnahme.

// body/interface.ts – das Einzige, was ein Client kennt
export type CommandStatus = { ok: true; ids?: Record<string, string> } | { ok: false; fehler: Fehler[] };
export type Bereich = 'aufgaben' | 'board' | 'kalender' | 'extern' | 'einstellungen';

export interface Body {
  // ---- Commands: Aufgaben
  schnellErfassen(c: { text: string }): Promise<CommandStatus>;

  statusSetzen(c: { aufgabeId: Id; status: StatusId | null }): Promise<CommandStatus>;
  aufgabeAbschliessen(c: { aufgabeId: Id }): Promise<CommandStatus>;
  aufgabeWiedereroeffnen(c: { aufgabeId: Id }): Promise<CommandStatus>;
  aufgabeVerwerfen(c: { aufgabeId: Id }): Promise<CommandStatus>;
  // ---- Commands: Buchungen
  buchungAnlegen(c: { aufgabeId: Id; datum: Datum; dauer: Minuten; start?: Uhrzeit; titel?: string }): Promise<CommandStatus>;  // Titel: Standard = Aufgabentitel
  buchungEintragen(c: { titel: string; beschreibung?: string; datum: Datum; dauer: Minuten; start?: Uhrzeit }): Promise<CommandStatus>;  // freie Buchung

Verarbeitung im Body (Beispiel)

async buchungAnlegen(c) {
  const fehler = pruefeEingabe(c);                       // Syntax: Datum gültig, Dauer > 0 …
  if (fehler.length) return { ok: false, fehler };
  const jetzt = this.uhr.jetzt(), buchungId = this.ids.neu();     // Provider
  const r = await this.domain.buchungAnlegen({ ...c, buchungId, jetzt }); // Domain entscheidet + speichert
  if (!r.ok) return r;
  if (this.einstellungen.autoVeroeffentlichen) await this.veroeffentlichen(buchungId);  // optional, Provider
  this.melde(['kalender', 'aufgaben', 'board']);
  return { ok: true, ids: { buchungId } };
}

async zeitraum({ von, bis }) {
  const heute = this.uhr.heute();
  const eigene = this.domain.kalender(von, bis, heute);        // Projektion
  const fremde = await this.kalenderCache.termine(von, bis);   // Provider (Cache, keine Netzlast)
  return fuegeZusammen(eigene, fremde, this.einstellungen.kapazitaet);  // pure Funktion im Body
}

Der Parser der Schnellerfassung ist eine pure Funktion im Body (body/schnellerfassung/parse.ts). Er braucht nur „heute“ als Parameter. schnellErfassen parst den Text und ruft dann intern aufgabeErfassen auf. Die Live-Vorschau verwendet denselben Parser, deshalb sieht der Nutzer schon beim Tippen genau das, was gespeichert wird.

6 Domain interface

Die Domain kapselt den Zugriff auf den Domain state. Statt Aggregaten verwendet sie Kontextmodelle pro Command: Für jede Entscheidung holt sie genau die Events, die dafür relevant sind (per Typ und Tag), baut daraus ein kleines Modell, prüft die Regeln und hängt neue Events an. Das Anhängen ist bedingt: Ist seit dem Lesen ein relevantes Event dazugekommen, wird der Command wiederholt oder abgelehnt. Das entspricht dem Prinzip der „Dynamic Consistency Boundary“.

// domain/interface.ts
export interface Domain {
  // Commands (Zeit & IDs kommen vom Body)
  aufgabeErfassen(c: { aufgabeId; jetzt; felder: AufgabeFelder; buchung?: BuchungEntwurf & { buchungId } }): Promise<Ergebnis>;
  aufgabeAendern(c: { aufgabeId; jetzt; aenderungen }): Promise<Ergebnis>;
  statusSetzen(c: { aufgabeId; status; jetzt }): Promise<Ergebnis>;
  aufgabeAbschliessen(c: { aufgabeId; jetzt }): Promise<Ergebnis>;
  buchungAnlegen(c: { buchungId; aufgabeId; datum; dauer; start?; jetzt }): Promise<Ergebnis>;
  buchungVerschieben(c: { buchungId; datum; start; jetzt }): Promise<Ergebnis>;
  buchungVerknuepfen(c: { buchungId; quelle; kalenderId; externeId; jetzt }): Promise<Ergebnis>;
  // … weitere analog zum Body

  // Queries (synchron aus Projektionen im Speicher)
  aufgaben(heute: Datum): AufgabenProjektion;   // inkl. gebuchter Zeit je Aufgabe
  board(): BoardProjektion;
  kalender(von: Datum, bis: Datum, heute: Datum): EigeneKalenderdaten;
  aufgabe(id: Id): AufgabeDetails | null;
  vorschlaege(art, praefix): string[];
  veroeffentlichungen(): Verknuepfung[];
}
// domain/commands/buchungAnlegen.ts – Kontextmodell statt Aggregat
export async function buchungAnlegen(es: EventStore, c) {
  const abfrage = { tags: [`aufgabe:${c.aufgabeId}`], typen: ['AufgabeErfasst', 'AufgabeAbgeschlossen', 'AufgabeWiedereroeffnet', 'AufgabeVerworfen'] };
  const { events, position } = await es.lesen(abfrage);
  const ctx = events.reduce(entwickle, { existiert: false, offen: false });   // pure
  if (!ctx.existiert) return fehler('Aufgabe unbekannt');
  if (!ctx.offen)     return fehler('Aufgabe ist abgeschlossen');
  return es.anhaengen([buchungAngelegt(c)], { bedingung: { abfrage, nachPosition: position } });
}

Projektionen

  • Beim Start liest die Domain alle Events einmal ein und baut daraus die Projektionen Aufgaben, Buchungen nach Datum, Board, Vorschläge und Verknüpfungen. Bei 50.000 Events dauert das unter einer Sekunde. Später kann ein Snapshot pro Projektion den Start weiter beschleunigen.
  • Nach jedem erfolgreichen Anhängen benachrichtigt der Event Store die Domain, und die Projektionen werden inkrementell nachgeführt. So sind Lesen und Schreiben getrennt (CQS), und jede Query ist trotzdem sofort aktuell.
  • Alles, was von „heute“ abhängt (Wiedervorlage sichtbar? Frist überfällig?), wird beim Abfragen mit dem übergebenen Datum ausgewertet und nicht in der Projektion gespeichert.

7 Provider interfaces

  abonnieren(cb: (e: GespeichertesEvent[]) => void): Abmelden;
}
interface Uhr         { jetzt(): Zeitpunkt; heute(): Datum; zeitzone(): string }
interface IdGenerator { neu(): Id }                               // ULID: zeitlich sortierbar

  kalenderAuflisten(v: Verbindung): Promise<KalenderInfo[]>;

8.4 Speicherort: Dropbox

Entschieden: Der Domain state liegt in der Dropbox, zum Beispiel unter ~/Dropbox/Apps/Rundblick/. Lokal unter ~/Library/Application Support/Rundblick/ liegen nur gerätebezogene Dinge: Kalender-Cache, sichtbare Kalender, Layouts.

Dropbox/Apps/Rundblick/
├─ events/
│  ├─ mac-ralf.jsonl        // jetzt: ein Gerät, eine Datei
│  └─ iphone-ralf.jsonl     // später: die iPhone-App schreibt ihre eigene Datei
└─ snapshots/               // optional, beschleunigt den Start; jederzeit löschbar

Heute arbeitest du allein auf einem Mac. Trotzdem empfehle ich von Anfang an eine Event-Datei pro Gerät. Das kostet fast nichts (ein Ordner statt einer Datei) und erspart später eine Migration:

  • Dropbox kann gleichzeitige Änderungen derselben Datei nicht zusammenführen. Daraus entstehen „Konfliktkopien“. Schreibt jedes Gerät nur in seine eigene Datei, kann das nicht passieren.
  • Jedes Gerät liest alle Dateien und mischt die Events zu einem Strom. Damit die Reihenfolge auf allen Geräten gleich ist, braucht jedes Event einen Zeitstempel, der geräteübergreifend vergleichbar ist. Dafür ist die Hybrid Logical Clock da.
  • Die Mac-App beobachtet den Ordner (fs.watch). Kommen neue Zeilen von einem anderen Gerät an, werden die Projektionen nachgeführt, und die Clients bekommen geaendert(…).
  • Das bedingte Anhängen (Konsistenzprüfung) gilt nur lokal. Konkurrierende Änderungen zweier Geräte (beide verschieben dieselbe Buchung) löst die Regel „späteres Event gewinnt“. Für eine Ein-Personen-App reicht das.

8.5 Was ist eine Hybrid Logical Clock (HLC)?

Ein Zeitstempel, der wie eine Uhrzeit aussieht, aber nie rückwärts läuft und geräteübergreifend eine eindeutige Reihenfolge ergibt. Er besteht aus zwei Teilen: (physische Zeit in ms, Zähler), dazu als Gleichstand-Entscheider die Geräte-ID.

  • Problem: Die Uhren von Mac und iPhone gehen nie exakt gleich. Geht das iPhone 30 Sekunden nach, bekommt ein Event, das es nach einem Mac-Event geschrieben hat, eventuell einen früheren Zeitstempel. Nach der Wanduhr sortiert, stünden die Events dann in falscher Reihenfolge.
  • Lösung: Jedes Gerät merkt sich den größten Zeitstempel, den es je gesehen hat, eigene wie fremde. Ein neues Event bekommt max(jetzt, größter gesehener). Ist das nicht größer als der bisherige Höchstwert, zählt der Zähler hoch. Dadurch liegt alles, was ein Gerät nach dem Lesen eines fremden Events schreibt, garantiert dahinter.
  • Ergebnis: Die Werte bleiben nahe an der echten Uhrzeit und sind deshalb lesbar und zum Anzeigen brauchbar. Sie sind trotzdem streng monoton und kausal korrekt, und alle Geräte sortieren identisch nach (hlc, geraet, id).
  • Für jetzt: Mit nur einem Gerät ist die HLC praktisch die Uhrzeit. Ins Event-Format (meta.hlc, meta.geraet) gehört sie trotzdem von Anfang an, damit eine spätere iPhone-App ohne Umschreiben dazukommen kann.

9 Google Calendar & iCloud

Entschieden: EventKit zuerst. Ein kleiner Swift-Helfer liest über EventKit alle in macOS eingerichteten Kalender (iCloud, Google …). macOS fragt einmal nach der Erlaubnis. Es gibt keine eigene Anmeldung, kein OAuth und kein CalDAV. Für die spätere iPhone-App ist das ein Vorteil, denn EventKit gibt es auf iOS genauso.

Grundsatz

  1. Lesen als Overlay. Externe Termine erscheinen in allen Kalendersichten. Pro externem Kalender ist einstellbar, ob er sichtbar ist und ob seine Termine Kapazität belegen. Sie werden nicht zu Events, weil sie fremder Zustand sind. Sie liegen im Cache.
  2. Veröffentlichen (optional, Phase 2): Eigene Buchungen werden per EventKit in einen eigenen Kalender „Rundblick“ geschrieben (z. B. in iCloud), damit andere die Belegung sehen. Termine werden normale Events. Reservierungen werden ganztägige Einträge mit „frei“-Transparenz und dem Titel ▭ 2 h · Angebot Hüttner. Die Verknüpfung speichert das Event BuchungVeroeffentlicht.
  3. Rückkanal (optional, Phase 3): Wird ein veröffentlichter Termin extern verschoben, erzeugt der Sync ein BuchungVerschoben mit meta.quelle = "sync". Für alle anderen externen Änderungen bleibt Rundblick der Master.
  4. Aus externem Termin eine Aufgabe oder Buchung machen: aufgabeErfassen bzw. buchungEintragen mit vorbelegtem Titel und Termin plus einem Verweis auf das Original.

Synchronisation mit EventKit

  • Der Swift-Helfer läuft als Kindprozess des Main-Prozesses und spricht JSON-Zeilen über stdin/stdout: {"op":"kalender"}, {"op":"termine","von":"…","bis":"…"}, {"op":"schreiben",…}.
  • EventKit meldet Änderungen selbst (EKEventStoreChanged). Der Helfer gibt sie als {"ereignis":"geaendert"} weiter, und der Body ruft synchronisieren() auf. Zusätzlich holt Rundblick die Termine beim Start, beim Fokussieren des Fensters und alle 5 Minuten (Nutzerwunsch). Die Synchronisation mit iCloud und Google erledigt macOS selbst.
  • Serien sind bereits aufgelöst: EventKit liefert Einzeltermine pro Zeitraum.
  • Der Cache hält das Fenster −30 / +180 Tage vor, damit Queries nie auf den Helfer warten.
  • Fehlt die Berechtigung oder stürzt der Helfer ab, ändert sich kein Domain state. Der Client zeigt einen Hinweis, zum Beispiel „Kalenderzugriff in den Systemeinstellungen erlauben“.

16 Phone App (PWA) – entschieden 18.11.2026

Ziel: TickTick auf dem Handy ersetzen – zuerst nur Aufgaben; Kalender später. Desktop-App und Phone App verwalten dieselben Aufgaben.

Entscheidungen: Weg B (Browser greift direkt auf die Dropbox zu, kein Server, keine Datendopplung) · Dropbox-App „Rundblick“ mit Zugriff nur auf den App-Ordner (Apps/Rundblick) · Hosting bei Netlify (nur Programmcode, keine Daten) · offline-first.

Aufbau

  • Unverändert übernommen: Domain, Body, Schema, Basis. Body-Proxy ruft das Body-Objekt im selben Fenster auf.
  • Neu: Web-Composition-Root und Browser-Provider – Event Store (lokal IndexedDB + Abgleich mit Dropbox), IDs (crypto.getRandomValues), Uhr, Einstellungen (localStorage); Kalender vorerst „nicht verfügbar“; Bilder zunächst lesend.
  • Gerätedatei: eigene Datei, z. B. events/iphone-ralf.jsonl; Reihenfolge über die Hybrid Logical Clock (8.4, 8.5). Die Desktop-App übernimmt sie über die Ordner-Beobachtung – dort ändert sich nichts.
  • Zugang: OAuth mit PKCE im Browser (nur App-Key, kein Secret), Refresh-Token auf dem Gerät.
  • Oberfläche: eigene Handy-Hülle aus den vorhandenen Bausteinen – unten Liste · Board · Logbuch, oben Schnellerfassung, Aufgabe als Vollbild-Ansicht; Touch statt Hover (Wischen/Detail statt Mülleimer beim Überfahren, weiterhin zweistufig; Reihenfolge per langem Drücken).

Offline-first

  • Service Worker speichert die App → startet auch ohne Netz. Alle bekannten Events liegen in IndexedDB; daraus entsteht der Stand wie am Desktop.
  • Jede Änderung wird sofort lokal gespeichert; eigene Events kommen in eine Warteschlange. Online: eigene Gerätedatei aus dem lokalen Speicher komplett neu hochladen (nur dieses Gerät schreibt sie; Revisionsprüfung), fremde Änderungen per Dropbox-Cursor holen, nach HLC einsortieren; danach Longpoll.
  • Gleichzeitige Änderungen: feingranulare Events → verschiedene Felder vertragen sich; dasselbe Feld → spätere Änderung (HLC) gewinnt.
  • Anzeige: Wolken-Symbol (Lucide Cloud / CloudUpload mit Anzahl / CloudOff), Tipp = Abgleich.
  • iOS: navigator.storage.persist(); sofort hochladen, damit keine Änderungen nur lokal liegen.
