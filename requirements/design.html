Rundblick – Architekturideen

Arbeitstitel · Entwurf vom 16.11.2026 · Electron-Desktop-App für Aufgaben, Board und Kalender mit Google Calendar und iCloud

Rundblick verwaltet eigene Daten (Aufgaben und ihre Buchungen) in einem Event Store und blendet fremde Daten (Termine aus Google Calendar und iCloud) daneben ein. Die Architektur folgt den Vorgaben: Client → Body → Domain/Provider, strikt nach CQS getrennt. Jeder Pfeil zeigt nur auf ein Interface, nie auf eine Implementation.

1 Leitbild & Begriffe

Überblick ist King. Das prägt die Architektur. Fast jede Interaktion endet damit, dass alle sichtbaren Sichten aktuell sein müssen: Liste, Board und Kalender, auch in eingeklappter Form. Daraus folgt:

  • Ein Command meldet nur Erfolg oder Misserfolg zurück. Danach erfahren alle Clients per Änderungsbenachrichtigung, welche Bereiche betroffen sind, und fragen ihre Queries neu ab.
  • Queries müssen sehr schnell sein (Ziel < 5 ms). Deshalb liegen Projektionen im Speicher. Die Datenmenge einer Person (Zehntausende Events) passt bequem hinein.
  • Erfassen muss ohne Kontextwechsel gehen. Dafür gibt es eine zweite Client-Oberfläche, das Schnellerfassungsfenster mit globalem Hotkey.

2 Architektur im Überblick

Client interface  kennt nur Body interface

Hauptfenster (UI) · Schnellerfassungsfenster (globaler Hotkey) · optional lokales REST API (für Raycast, Kurzbefehle, Skripte) · Menüleisten-Symbol. Nur hier sind Svelte, Electron-IPC, HTTP-Server und globalShortcut bekannt.

▼ Commands / Queries · ▲ CommandStatus / Query-Ergebnisse / Änderungsbenachrichtigungen

Body interface  kennt Domain + Provider interfaces

Koordiniert jede Anfrage. Holt Uhrzeit und IDs von Providern, ruft die Domain auf, fügt eigene und externe Kalenderdaten für Queries zusammen, stößt die Synchronisation an und veröffentlicht Buchungen extern. Parst die Schnellerfassung. Meldet Änderungen.

Domain interface  kennt nur den Domain state provider

Entscheidet über Commands und beantwortet Fragen zum eigenen Zustand. Für jeden Command baut sie sich aus dem Event Store ein Kontextmodell, prüft die Regeln und hängt neue Events an. Queries liest sie aus Projektionen, die laufend aus den Events nachgeführt werden.

  • Aufgaben, Status, Buchungen, Board-Konfiguration, Verknüpfungen zu externen Kalendern

Provider interfaces

  • Uhr · IdGenerator
  • Kalenderquelle (Google, iCloud, optional EventKit)
  • Externer Kalender-Cache
  • Geheimnisspeicher (Keychain)
  • Einstellungen · Benachrichtiger

Domain state provider: Event Store

Append-only, Abfrage nach Event-Typen und Tags, bedingtes Anhängen (optimistische Konsistenz). Implementierung zunächst als JSONL-Datei.

Die Regeln werden mit dependency-cruiser im CI geprüft. Ein Verstoß bricht den Build.

Warum bekommt die Domain keine Uhr? Damit ist die Domain deterministisch: Gleiche Events und gleicher Command ergeben immer dieselben neuen Events. Der Body holt jetzt und neue IDs bei den Providern und übergibt sie als Parameter. Das passt zur Vorgabe, dass die Domain nur den Domain state provider kennt.

  • Preload/contextBridge stellt nur drei Funktionen bereit: command(name, payload), query(name, payload) und onChange(cb). Die Typen kommen aus body/interface.ts. Der Renderer sieht also genau das Body interface und nichts sonst. Einstellungen: contextIsolation an, sandbox an, nodeIntegration aus.
  • Body und Domain laufen im Main-Prozess. Die Synchronisation mit den externen Kalendern läuft dort asynchron und blockiert nichts. Wird sie zu schwer, wandert der Kalender-Provider in einen utilityProcess, ohne dass sich am Body etwas ändert.
  • Das lokale REST API ist ein zweiter Client derselben Body-Schnittstelle: POST /commands/schnellErfassen, GET /queries/heute. So lassen sich zum Beispiel Raycast, Alfred oder iOS-Kurzbefehle anbinden (im LAN mit Token).

4 Client interface

Das Client interface ist die Außenseite der App, also das, womit Menschen und andere Programme interagieren. Die Implementierung übersetzt Gesten in Commands und Queries des Body und stellt Ergebnisse dar. Sie enthält keine Fachlogik. Erlaubt ist nur Darstellungslogik: Layout von Überlappungen, Pixel ↔ Zeit, Zoom, Fokuszustand.

Aufgabe aufs Reservierungsband ziehencommand.buchungAnlegen({ aufgabeId, datum, dauer: 60 })
Aufgabe ins Zeitraster ziehencommand.buchungAnlegen({ aufgabeId, datum, start, dauer })

UI-Zustand wie Fokus, Zoom, Kalendersicht oder Splitter-Position gehört nicht zum Domain state. Er wird über command.einstellungMerken im Einstellungs-Provider abgelegt, ganz ohne Events.

5 Body interface

Eine Methode pro Command und pro Query. Commands verändern den Zustand und liefern nur einen CommandStatus. Queries verändern nichts und liefern Daten. IDs neuer Objekte stehen im Status, sonst wüsste der Client nicht, was er gerade angelegt hat. Das ist die übliche, CQS-verträgliche Ausnahme.

// body/interface.ts – das Einzige, was ein Client kennt
export type CommandStatus = { ok: true; ids?: Record<string, string> } | { ok: false; fehler: Fehler[] };
export type Bereich = 'aufgaben' | 'board' | 'kalender' | 'extern' | 'einstellungen';

export interface Body {
  // ---- Commands: Aufgaben

Verarbeitung im Body (Beispiel)

async buchungAnlegen(c) {
  const fehler = pruefeEingabe(c);                       // Syntax: Datum gültig, Dauer > 0 …
  if (fehler.length) return { ok: false, fehler };
  const jetzt = this.uhr.jetzt(), buchungId = this.ids.neu();     // Provider
  const r = await this.domain.buchungAnlegen({ ...c, buchungId, jetzt }); // Domain entscheidet + speichert
  if (!r.ok) return r;
  if (this.einstellungen.autoVeroeffentlichen) await this.veroeffentlichen(buchungId);  // optional, Provider
  this.melde(['kalender', 'aufgaben', 'board']);
  return { ok: true, ids: { buchungId } };
}

async zeitraum({ von, bis }) {
  const heute = this.uhr.heute();
  const eigene = this.domain.kalender(von, bis, heute);        // Projektion
  const fremde = await this.kalenderCache.termine(von, bis);   // Provider (Cache, keine Netzlast)
  return fuegeZusammen(eigene, fremde, this.einstellungen.kapazitaet);  // pure Funktion im Body
}

Der Parser der Schnellerfassung ist eine pure Funktion im Body (body/schnellerfassung/parse.ts). Er braucht nur „heute“ als Parameter. schnellErfassen parst den Text und ruft dann intern aufgabeErfassen auf. Die Live-Vorschau verwendet denselben Parser, deshalb sieht der Nutzer schon beim Tippen genau das, was gespeichert wird.

6 Domain interface

Die Domain kapselt den Zugriff auf den Domain state. Statt Aggregaten verwendet sie Kontextmodelle pro Command: Für jede Entscheidung holt sie genau die Events, die dafür relevant sind (per Typ und Tag), baut daraus ein kleines Modell, prüft die Regeln und hängt neue Events an. Das Anhängen ist bedingt: Ist seit dem Lesen ein relevantes Event dazugekommen, wird der Command wiederholt oder abgelehnt. Das entspricht dem Prinzip der „Dynamic Consistency Boundary“.

// domain/interface.ts
export interface Domain {
  // Commands (Zeit & IDs kommen vom Body)
  aufgabeErfassen(c: { aufgabeId; jetzt; felder: AufgabeFelder; buchung?: BuchungEntwurf & { buchungId } }): Promise<Ergebnis>;
  aufgabeAendern(c: { aufgabeId; jetzt; aenderungen }): Promise<Ergebnis>;
  statusSetzen(c: { aufgabeId; status; jetzt }): Promise<Ergebnis>;
  aufgabeAbschliessen(c: { aufgabeId; jetzt }): Promise<Ergebnis>;
  buchungAnlegen(c: { buchungId; aufgabeId; datum; dauer; start?; jetzt }): Promise<Ergebnis>;
  buchungVerschieben(c: { buchungId; datum; start; jetzt }): Promise<Ergebnis>;
  buchungVerknuepfen(c: { buchungId; quelle; kalenderId; externeId; jetzt }): Promise<Ergebnis>;
  // … weitere analog zum Body

  // Queries (synchron aus Projektionen im Speicher)
  aufgaben(heute: Datum): AufgabenProjektion;
  board(): BoardProjektion;
  kalender(von: Datum, bis: Datum, heute: Datum): EigeneKalenderdaten;
  aufgabe(id: Id): AufgabeDetails | null;
  vorschlaege(art, praefix): string[];
  veroeffentlichungen(): Verknuepfung[];
}
// domain/commands/buchungAnlegen.ts – Kontextmodell statt Aggregat
export async function buchungAnlegen(es: EventStore, c) {
  const abfrage = { tags: [`aufgabe:${c.aufgabeId}`], typen: ['AufgabeErfasst', 'AufgabeAbgeschlossen', 'AufgabeWiedereroeffnet', 'AufgabeVerworfen'] };
  const { events, position } = await es.lesen(abfrage);
  const ctx = events.reduce(entwickle, { existiert: false, offen: false });   // pure
  if (!ctx.existiert) return fehler('Aufgabe unbekannt');
  if (!ctx.offen)     return fehler('Aufgabe ist abgeschlossen');
  return es.anhaengen([buchungAngelegt(c)], { bedingung: { abfrage, nachPosition: position } });
}

Projektionen

  • Beim Start liest die Domain alle Events einmal ein und baut daraus die Projektionen Aufgaben, Buchungen nach Datum, Board, Vorschläge und Verknüpfungen. Bei 50.000 Events dauert das unter einer Sekunde. Später kann ein Snapshot pro Projektion den Start weiter beschleunigen.
  • Nach jedem erfolgreichen Anhängen benachrichtigt der Event Store die Domain, und die Projektionen werden inkrementell nachgeführt. So sind Lesen und Schreiben getrennt (CQS), und jede Query ist trotzdem sofort aktuell.
  • Alles, was von „heute“ abhängt (Wiedervorlage sichtbar? Frist überfällig?), wird beim Abfragen mit dem übergebenen Datum ausgewertet und nicht in der Projektion gespeichert.

Feingranular statt AufgabeGeaendert. Jedes Event hat eine fachliche Bedeutung („Frist gesetzt“). 8.4 Speicherort & mehrere Rechner

Am Anfang liegt alles unter ~/Library/Application Support/Rundblick/. Soll der Bestand über Dropbox oder iCloud Drive auf mehreren Macs verfügbar sein, bietet sich eine Event-Datei pro Gerät an (events/<geraet>.jsonl). Jedes Gerät schreibt nur in seine eigene Datei, deshalb gibt es keine Schreibkonflikte im Dateisystem. Gelesen wird die Vereinigung aller Dateien, sortiert nach Zeitstempel (Hybrid Logical Clock) und dann nach ID. Fachliche Konflikte (zwei Geräte verschieben dieselbe Buchung) löst die Regel „letztes Event gewinnt“, was für eine Ein-Personen-App ausreicht. Der Cache externer Termine bleibt pro Gerät lokal.

9 Google Calendar & iCloud

Grundsatz

  1. Lesen als Overlay. Externe Termine erscheinen in allen Kalendersichten und zählen zur Auslastung. Sie werden nicht zu Events, weil sie fremder Zustand sind. Sie liegen im Cache.
  2. Veröffentlichen (optional, Phase 2): Eigene Buchungen werden in einen eigenen Kalender „Rundblick“ geschrieben, damit andere die Belegung sehen. Termine werden normale Events. Reservierungen werden ganztägige Einträge mit „frei“-Transparenz und dem Titel ▭ 2 h · Angebot Hüttner. Die Verknüpfung speichert das Event BuchungVeroeffentlicht.
  3. Rückkanal (optional, Phase 3): Wird ein veröffentlichter Termin extern verschoben, erzeugt der Sync ein BuchungVerschoben mit meta.quelle = "sync". Für alle anderen externen Änderungen bleibt Rundblick der Master.
  4. Aus externem Termin eine Aufgabe machen: aufgabeErfassen mit vorbelegtem Titel und Termin plus einem Verweis auf das Original.

Synchronisation

  • Der Body steuert sie über den Command synchronisieren(). Ausgelöst wird er per Zeitgeber (alle 5 min), beim Fokussieren des Fensters und beim Start.
  • Google: inkrementell per syncToken. Ein HTTP 410 bedeutet Neuaufbau. Push-Kanäle brauchen einen öffentlichen HTTPS-Endpunkt und kommen für eine Desktop-App deshalb nicht in Frage.
  • iCloud: CalDAV sync-collection (RFC 6578) oder ctag-Vergleich plus calendar-query für das Fenster −30 / +180 Tage.
  • Fehler (offline, Token abgelaufen) verändern keinen Domain state. Der Client zeigt einen dezenten Hinweis „Google seit 14:20 nicht aktualisiert“.
Abkürzung für macOS: EventKit. Wenn Google und iCloud ohnehin in der macOS-App „Kalender“ eingerichtet sind, kann ein winziger Swift-Helfer über EventKit alle Kalender lesen und schreiben. Dafür sind kein OAuth, keine Google-Cloud-Console, kein App-Passwort und kein CalDAV-Code nötig. Die Architektur bleibt dieselbe, es ist nur eine weitere Implementierung von Kalenderquelle. Empfehlung: mit EventKit beginnen (am schnellsten am Ziel), Google REST und CalDAV als portable Implementierungen später nachziehen.

13 Offene Fragen & Empfehlungen

1

Direkt im Kalender eingetragene Reservierung: eigene Aufgabe oder nicht?

Empfehlung: Jede Buchung gehört zu einer Aufgabe. reservierungEintragen legt still eine Aufgabe mit demselben Titel an. So bleibt das Modell einfach, und nichts verschwindet aus dem Überblick.

2

Spalte „Fertig“ und Abschließen

Empfehlung: Beides getrennt halten. „Fertig“ ist ein Status zum Prüfen und Abrechnen, das Abschließen bleibt ein bewusster Klick (in den Entwürfen der Knopf „✓ abschließen“). Alternative: eine Einstellung „Ziehen nach Fertig schließt ab“.

3

Brauchen Buchungen eine eigene Notiz oder einen eigenen Titel? (z. B. „Teil 2: Kalkulation“)

Empfehlung: optionales Feld notiz ab Version 1, angezeigt als „Titel · Notiz“.

4

Wiederkehrende Aufgaben (jeden Monat „Reisekosten einreichen“)

Gehört nicht zum ersten Wurf. Passt später als WiederholungFestgelegt plus Erzeugung beim Abschließen.

5

Vergangene Buchungen: Soll man „wahrgenommen / nicht geschafft“ markieren können? Das würde die Kalenderrückschau zum Werkzeug machen.

Empfehlung: zunächst nicht. Nicht geschaffte Reservierungen erscheinen aber im Überblick als Hinweis „3 Reservierungen von gestern ohne Abschluss“.

6

Tageskapazität und Arbeitszeitfenster für die Auslastung (Entwurf: 8 h, 7–21 Uhr)

als Einstellung, eventuell pro Wochentag

7

Externe Anbindung: EventKit (nur Mac, schnell) oder Google REST + CalDAV (portabel, aufwendiger)?

Empfehlung: EventKit zuerst, siehe 9

8

Mehrere Rechner über Dropbox?

Möglich mit einer Event-Datei pro Gerät (8.4). Das Event-Format sollte deshalb von Anfang an meta.geraet und eine HLC-Zeit enthalten.
